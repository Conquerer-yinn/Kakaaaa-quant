# Tushare 频次与超时约束

## 背景

在情绪指标任务的实际试跑过程中，已经真实遇到过以下问题：

1. `当前接口达到请求上限，请稍后重试`
2. `每分钟最多访问该接口 1500 次`
3. `请求超时`
4. 网络连接失败或网关波动

这说明后续 AI 写 Tushare 相关代码时，不能只考虑字段口径，还必须同时考虑请求节奏和失败重试。

## 当前项目约定

1. 默认请求延迟不低于 `0.5s`
2. 所有常用 Tushare 请求统一通过 `data_engine/tushare_api.py`
3. 常见限流与超时错误要做指数退避重试
4. 单日失败不应直接让整段任务崩掉，但失败日期不能写入主表
5. 日常任务优先走增量更新，不要每次都全量重拉历史

## 当前已落地策略

1. `TushareDataEngine` 统一封装：
   - `get_trade_calendar`
   - `get_daily_quotes`
   - `get_daily_basic`
   - `get_limit_list`
   - `get_stk_limit`
   - `get_stock_basic`
2. 内置重试关键词包括：
   - 请求上限
   - 每分钟最多访问该接口
   - 请求过于频繁
   - 请求超时
   - 网络连接失败
3. 重试等待采用指数退避：`delay * 2^attempt`

## 后续写代码时的建议

1. 能复用已有主表时，不要全量补历史
2. 一个任务里尽量先把同一交易日需要的接口拉全，再进入下一交易日
3. 不要在细粒度循环里为每只股票反复单独请求接口，优先批量接口
4. 先设计最小字段集，避免为了“可能以后用到”就多拉很多字段
5. 写任务时默认考虑“失败补跑”而不是“单次必须全成功”

## 备注

官方频次限制与账号权限有关，不同账号可能不同。
因此项目内应以“保守节奏 + 增量优先 + 自动重试”为默认策略，而不是把接口打到上限再处理。
