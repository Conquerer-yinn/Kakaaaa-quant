### 3. 关于“综合任务 vs 多任务链”的重要结论

围绕 `run_market_sentiment.py` 展开了关键讨论。

通过查看 `market/` 当前文件结构，确认：

- `run_market_sentiment.py` 已经不是一坨完全耦合的脚本
- 其外部已经有多组情绪指标模块：
  - `sentiment_market.py`
  - `sentiment_height.py`
  - `sentiment_chinext.py`
  - `sentiment_feedback.py`
  - `sentiment_stat.py`
- 当前更接近：
  - 一个综合研究任务入口
  - 多个内部指标模块
  - 最终写入同一个工作簿

最终形成的共识是：

- 不需要为了“多任务链”而强行把 `run_market_sentiment.py` 拆成很多独立入口
- 也不需要为了工程整齐，把一个主题一致的研究工作簿拆成多个 Excel
- 现在更合理的解释不是“必须多任务”，而是要区分：
  - 研究成品入口
  - 内部指标组件
  - 数据获取与输出层

进一步固化为一条重要规则：

- `market` 下任务分两类：
  1. 独立标准任务
  2. 综合研究任务

当前代表分别为：

- 独立标准任务：`run_daily_basics.py`
- 综合研究任务：`run_market_sentiment.py`

并明确：

- 允许综合研究任务输出同一个 Excel 的多个 sheet
- 不因为引入 API，就反向强拆综合任务

### 4. 关于“现在能不能直接做 FastAPI”的判断

用户进一步问：

- 现在是不是可以直接做 FastAPI
- 还是任务还不够标准化

在查看当前项目后得出的判断是：

- 现在已经不是“完全不能做 FastAPI”的状态
- 但也还不适合做重型任务平台
- 更适合做“最小 FastAPI 封装层”

建议第一版只做：

- `GET /health`
- `GET /tasks`
- `POST /tasks/daily-basics/run`
- `POST /tasks/market-sentiment/run`

并明确当前阶段不做：

- 数据库
- 任务队列
- 复杂 `task_id` 生命周期
- 通用任务平台
- 为 API 反向大重构现有任务

### 7. 本次阶段性结论

本窗口截至当前形成的主要结论有：

1. 当前阶段不应强行把综合研究任务拆成多个独立任务。
2. 当前阶段允许综合研究任务输出同一个 Excel 的多个 sheet。
3. `market` 下任务明确分成两类：
   - 独立标准任务
   - 综合研究任务
4. FastAPI 当前适合做最小封装层，不适合直接做完整任务平台。
5. 当前最小服务层已经完成，并通过真实任务联调验证可用。
6. 下一阶段更自然的方向是补一条最小消息通知链路。
